# Why we picked Postgres over Mongo — postmortem

Writing this 18 months after the fact because it keeps coming up in conversations.

**The original decision (mid-2024)**: Crucible needed a primary store. Considered Postgres, Mongo, SQLite. Picked SQLite. But there was a moment — around the 6-month mark — when I considered migrating to either Postgres (server-based, relational) or Mongo (document, flexible schema). This note is about that fork; the migration didn't happen, SQLite still wins, but the reasoning for *not* picking Mongo is worth recording because the same temptation comes up in other contexts.

**The case for Mongo at the time**:
- Crucible's data is hierarchical (tasks contain assumptions; assumptions reference evidence). Document model fits this naturally.
- Schema evolution — I was still figuring out the data model. Mongo's flexible schema seemed to suit a moving target.
- "Don't fight the database." The pitch was that storing JSON-shaped data in Postgres would force me to either flatten the structure or use JSONB columns, neither ideal.

**The case against Mongo, which won**:
- The hierarchical data has *constraints*. Every assumption belongs to exactly one task; every evidence event references one or more assumptions. These are *relational* invariants, and relational databases enforce them in a way document stores don't. The day I had a bug where an assumption was orphaned (its task got deleted, the assumption survived) I'd be debugging it the hard way in Mongo.
- "Flexible schema" sounds good until you're 3 years in and your data has 14 different shapes from various refactor passes. Strict schemas force you to migrate when you change shape; flexible schemas let you defer the migration forever, which is bad in expectation.
- The query patterns I needed turned out to be deeply relational — joins across tasks, assumptions, and evidence to build the dependency graph. Mongo's aggregation pipeline can do this but it's awkward; SQL does it natively.

**The deeper principle**: "match the storage to the natural shape of your data" is a real heuristic, but the shape of your data is the *constraints*, not the structure. A hierarchical data shape with relational constraints is still relational data. Mongo's pitch is for hierarchical data with no relational constraints — most data isn't actually that.

**Where this shows up elsewhere**: same family of mistakes as picking a non-relational database for inherently relational data. Same family as using a heap-based factor portfolio when the actual constraints are turnover-and-capacity-bounded — the structure looks right at first glance and is wrong on inspection. Same family as choosing pure exploitation training when the horse has already plateaued — the structure looks right at first glance.

**For Crucible specifically**: SQLite has been the right call. If I outgrew SQLite, I'd go to Postgres. Mongo would come up in other people's conversations and stay out of mine.
