# Choosing a vector DB — comparison

Crucible needs a vector index for semantic search across tasks/decisions/evidence. Surveying options.

**Requirements**:
- Local-first. The whole point of Crucible is the data lives on my laptop. No mandatory cloud component.
- Reasonable performance up to 100k vectors (current size: 8k; 100k is a 5-year projection).
- Reasonable cost — happy to pay something, but not enterprise-tier.
- Solid metadata filtering. I want to combine semantic similarity with structural filters (e.g., "find similar decisions tagged 'finance'").

**Candidates**:

1. **SQLite + sqlite-vec extension**. Pros: same SQLite I'm already using, no new infra, transactions span both metadata and vectors. Cons: performance on large vectors not as fast as purpose-built. For 100k vectors of dim 1024, 100ms+ per query. Acceptable for Crucible.
2. **LanceDB**. Pros: file-based (no server), well-maintained, fast for the size class, good Python + JS APIs. Cons: another dependency; my SQLite story breaks slightly.
3. **Qdrant local**. Pros: very fast, good filtering. Cons: requires a running server process; doesn't fit the local-first model as cleanly.
4. **DuckDB + VSS**. Pros: DuckDB is excellent for analytical queries; the VSS extension is fast. Cons: another dependency layer; less proven in production for vector use specifically.
5. **No vector DB — just compute on-the-fly**. Pros: zero infrastructure. Cons: at 100k vectors, computing cosine against all of them per query takes seconds; not acceptable.

**Decision**: SQLite + sqlite-vec. Slightly worse performance than the purpose-built options, but the architectural simplicity wins. One file. One backup story. One query language. The 5-year projection of 100k still fits comfortably under 200ms. If I outgrow it, migration to LanceDB is straightforward (the embedding generation is the same; only the storage layer changes).

**Generalised principle**: for personal-scale tooling, *consolidation* of dependencies usually beats specialisation. The hidden cost of every additional storage system is the cognitive load of remembering its quirks, the operational load of backing it up, the upgrade-path risk. A slightly slower system that's already in your toolkit is usually better than a faster one that's new.

**Connection back**: this is the same shape as choosing factor weights. The optimal weighting on paper might differ from the practical weighting once you account for the maintenance cost of constantly rebalancing to optimal. The friction-aware optimum is rarely the friction-free optimum.
