# Idempotency keys for write-safe APIs

Notes from refactoring Crucible's mutation API to use idempotency keys properly.

**The problem**: client retries are unavoidable in any system with imperfect networks. Default behavior is "if I don't get a 200, retry the request." If the server actually processed the first request and the response got lost, the retry creates duplicate state. Bad.

**The standard solution**: idempotency keys. The client generates a UUID per *logical operation* (not per HTTP retry). The server stores a mapping from key → result for some retention period. On retry: if the key is known, return the stored result; if not, process and store.

**Subtleties**:
1. **Key scoping**. The key must be unique per user account, not globally. Otherwise users could collide. Implementation: key the lookup table on (user_id, idempotency_key).
2. **Retention**. Too short → late retries get reprocessed. Too long → storage bloat. Sweet spot for Crucible: 24 hours. Longer for high-value mutations like decision recording.
3. **In-flight handling**. What happens when the same key arrives twice while the first is still processing? Two options: lock and serialise (correct, slow); or return a 409 "request in flight" and let the client retry. I went with lock-and-serialise.
4. **Response stability**. The stored response has to actually be deterministic for the operation. If the operation includes a server-generated timestamp, the second response should return *the same* timestamp from the first invocation, not a new one.

**Connection to systems thinking**: idempotency is structurally similar to the way good handler-and-horse work treats repetition. Doing the *same* aid twice should produce the same effect. If aid-then-aid produces compound action (the horse builds up to a stronger response over multiple cues), the system isn't idempotent — it's accumulating state from previous cues. Sometimes you want that (some training intentionally builds reactivity); sometimes you really don't (you want a calm, predictable response that doesn't depend on aid history).

**Generalised principle**: any system with potentially unreliable communication channels needs to choose idempotency boundaries deliberately. The choice ripples through every layer. Banks built their whole transaction model on this. Trading systems likewise — duplicate trade prevention is essentially the same problem in a different domain. The carpenter's "measure twice, cut once" is a non-software analogue.

**Action item for Crucible**: apply the same principle to the local CLI. Currently `crucible add-task "..."` will create a new task each time it's run. Should accept an optional `--id` flag and reuse existing if specified. Small change; reduces accidental duplicates.
