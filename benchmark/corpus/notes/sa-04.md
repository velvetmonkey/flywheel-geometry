# Event sourcing for financial pipelines

Notes from a conversation with the systems team at Meridian. We're considering moving the desk's signal-generation pipeline to an event-sourced architecture from the current state-machine model.

**The current state**: every signal-generation run produces a snapshot. Snapshots are stored, but the *path* through which a snapshot was reached isn't. If we discover a bug in retrospect, we have to re-run from scratch with patched code; we can't just inspect what data flowed through which step.

**The event-sourced version**: every input becomes an event. Events are append-only. The pipeline's state at any point is the *fold* of all events up to that point. Bug discovery means replaying events with corrected logic; root cause analysis means inspecting the events themselves rather than guessing what got into the snapshot.

**The benefits I expect**:
- Audit trail without effort. Every result is reproducible by replaying the events.
- Debugging through replay rather than through forensics. "Why did the model produce this trade on Tuesday?" — we can replay Tuesday's events and watch the state evolve.
- Easier blue/green deployment. Run the new version of the pipeline on the same event stream as the old version; compare outputs.

**The costs**:
- Storage. Events are smaller than snapshots individually but accumulate fast. Need a tiered storage policy — hot events on SSD for the last quarter, warm on archive.
- Schema evolution. Once you've stored 10 million events with one schema, changing the schema is hard. Need versioned event schemas from day one.
- Mental model overhead. The team is used to thinking about "current state." Thinking in terms of "events that produced state" is a shift. Will require pairing on the first few migrations.

**Connection back**: this is structurally the same as keeping a running journal of every reasoning step rather than only the conclusions. Every analyst at Meridian effectively keeps such a journal in their notes; the firm doesn't aggregate them, so we lose the institutional learning that would come from being able to replay good and bad reasoning chains. Event sourcing on the pipeline is the engineered version of the same hygiene applied to the analyst.

**Pattern from elsewhere**: event sourcing in software is structurally identical to the way Bayesian updating in interpretability research treats activations. Every "prior + evidence → posterior" step is recoverable. The current state isn't the source of truth; the *sequence* is.

**Action item**: prototype the event-sourced version on a single sub-strategy before committing to the full migration. Pick the lowest-volume one (small-cap value sleeve) and run both architectures in parallel for a quarter. Measure observed bug-resolution time and audit-query time on each.
